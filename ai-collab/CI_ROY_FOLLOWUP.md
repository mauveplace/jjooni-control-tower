# CI-green to ROY final-review dispatch (opt-in, default-branch only)

## Motivation

A GitHub PR commit triggers `pull_request.synchronize` before the GitHub Actions CI completes. A Work webhook fired for that event may see `CI_PENDING`, and cannot rely on being retriggered by the subsequent CI status transition. As observed on [isolated PR #430](https://github.com/mauveplace/jjooni-control-tower/pull/430), the source-fix Work run and 136/136 green CI succeeded but the Work webhook did not create the final-review issue.

The GitHub Actions `workflow_run.completed` trigger, restricted to the existing **AI Collaboration Read-Only Contract** workflow and `pull_request`/success, is the deterministic handoff. Code checked out and executed by this privileged workflow is **trusted default-branch code, never PR HEAD or artifacts**.

## Exact security boundaries

1. `ai-collab/ci_roy_followup.py` validates a fresh, successful CI run ID/head SHA with the GitHub API, then resolves the live **open, non-draft, non-merged** PR. It must be a same-repository, `main`-targeting `[AI-COLLAB]` PR with `experiment/ai-collab-` branch prefix.
2. All PR files must be under `ai-collab/` or `ai-collab-dispatch/`. The PR must add/modify exactly one task JSON whose name matches its task_id, repository, base, `SYSTEM_REVIEW_ONLY`, `USER_APPROVAL_REQUIRED` and required reviewer `ROY`.
3. **Future tasks require explicit opt-in** by adding `"auto_roy_review_after_ci": true` to their task JSON. A hardcoded, one-PR exception for the already authorized isolated **PR #430 / D-261113-L2-CI-DISPATCH-035** allows existing test evidence to close without rewriting its immutable task contract.
4. The current HEAD must be exactly one ordinary commit after a **genuine GitHub Claude-app ROY NEEDS_CHANGES** review of the immediately preceding SHA. The correction commit must modify exactly one non-test `ai-collab/` file. A second ROY review already present causes skip, never a third review.
5. Before writing, enumerate all Issues (open and closed) and compare the full **title and first-line V1 marker + Target-PR, Task-ID, Expected-HEAD, Mode, Requested-By**. Ignore unrelated issue #330 progress comments; an Issue search mentioning the same task is not a duplicate by itself. Serialize CI workflow runs by head SHA. GitHub Issues has no atomic unique constraint, so a third-party simultaneous creator could still race; do not claim formal exactly-once.
6. **Only permitted write:** one `[AI-COLLAB][ROY-REQUEST]` GitHub Issue requesting ROY's *second and final* read-only review. The separate Claude `issues.opened` Routine verifies pinned PR HEAD and posts independently evidenced PASS / NEEDS_CHANGES / BLOCKED.
7. Workflow token permissions: `contents: read`, `actions: read`, `pull-requests: read`, `issues: write`. No credentials are logged. No source edit, branch push, main merge, deployment, external billing, private user data, financial actions, or trading.

## Observable acceptance and rollout

- The existing PR #430 has a correct Work-origin source-only fix `cb7633b1d869b39cb9ff5833dcdace9e0283950e` and [successful CI run #43381251287](https://github.com/mauveplace/jjooni-control-tower/actions/runs/43381251287), but no final ROY issue yet. Deployment of this workflow alone **cannot retroactively replay** that completed CI event. A *new* matching GitHub workflow_run event is required for a real automatic-dispatch proof. Never manufacture an issue in chat and claim it was generated by the workflow.
- Validate the dispatcher with its isolated unit tests, GitHub workflow syntax/checks, a genuine new CI success event and independent ROY review before declaring production healthy.
- Once GitHub Actions is proven to be the sole issue creator, remove/disable the CI→Issue write exceptions in the existing Work webhook and hourly fallback. Those Work tasks may continue to **monitor** status, notify on a missing ticket, and follow the established user-approval release gate.
- For `CI_PENDING` do not create a ticket early. A later successful `workflow_run.completed` will provide a fresh verified event; do not poll frequently.
- If Workflow token lacks Issue creation permission, fail visibly and request owner action instead of falsifying completion. No workflow may broaden GH token permissions without a new independent review.
